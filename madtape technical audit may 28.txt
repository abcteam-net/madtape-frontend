# Madtape.com — Technical Audit

---

## 1. Executive Summary

Madtape is a React-based single-page application (SPA) hosted on **GitHub Pages**. The homepage and all SPA-routed views load correctly via client-side navigation, but every URL accessed directly (typed into the browser, opened via link share, bookmarked, or followed from a search engine) returns a **GitHub Pages 404 error**. This affects every route in the application — including legal pages, video pages, creator profiles, and all core platform sections.

Secondary issues include: no actual video files behind the player, all footer navigation links are dead (`href="#"`), the AI Cinema index has 0 data entries, multiple film card thumbnails are broken on inner pages, platform stats appear to be hardcoded dummy values, and the meta description is inconsistent across pages. Despite these issues, Firebase Auth is initialized correctly, the search function works, the sign-in/register modal functions, and SEO fundamentals on the homepage are mostly solid.

## 2. Critical Technical Issues

### 2.1 Direct URL Access Returns GitHub Pages 404 — All Routes

**Root cause:** The site is a SPA (React with client-side routing) hosted on GitHub Pages. GitHub Pages has no server-side routing fallback, so any URL that is not literally a file path returns its default 404 page. The solution is a `404.html` redirect trick or migration to a host that supports SPA routing (Netlify, Vercel, Cloudflare Pages, etc.).

### 2.2 No Video Content in Video Player

On the video detail page (`/video/glass-hour` and presumably all others), clicking the play button results in a completely black screen with no video loading. The player renders UI chrome (play button, timeline bar, duration, HD badge) but no video file is attached. No network request for a video file was observed. The only functional links in the footer are the five legal/policy links in the bottom bar (`/rules`, `/privacy`, `/terms`, `/cookie-policy`, `/dmca`) — which all 404 on direct access (see 2.1 above).

## 6. SEO / Metadata Issues

### 6.1 Homepage Meta Description Inconsistency

The homepage has **two different meta descriptions** defined: the `<meta name="description">` tag reads "Stream the best 15-second cinematic AI films. Join creators, upload projects, and compete in standard generative challenge pools." The OG description (`og:description`) reads "Discover, stream, and generate cinematic short-form AI films. The premier global hub for emerging AI filmmakers, cinematic challenges, and latent space explorations." These should be identical.

Additionally, "compete in standard generative challenge pools" is awkward/generic-sounding copy that should be replaced with more specific messaging.

### 6.2 Canonical Tag on Sub-Routes Inherits `/upload`

When the user navigates to `/upload` (or is on the upload page), the canonical URL is set to `https://madtape.com/upload`. This appears to be correct per-page canonical behavior. However, this needs to be verified across all routes to ensure canonical tags update dynamically with each SPA route change. If the canonical tag doesn't update, all pages will report the same canonical URL to search engines.

### 6.3 No Schema Markup Beyond WebSite

The homepage has a single JSON-LD block of type `WebSite` with a `SearchAction` pointing to `/search?q={search_term_string}`. There is no structured data for VideoObject, Person, BreadcrumbList, or FAQPage — all of which would be highly relevant for a film platform.

### 6.4 The `robots.txt` Disallows `/search` — a Publicly Accessible Route

`robots.txt` has `Disallow: /search` for all crawlers. The search results page is publicly accessible and contains user-generated content (film titles, creator names) that has SEO value. This may be intentional but deserves review.

### 6.5 All Inner Pages Appear to Share the Same Meta Title

The `<title>` tag on all observed inner pages reads "Madtape AI — The Home of Short-Form AI Cinema" rather than a page-specific title (e.g., "Glass Hour — AI Short Film — Madtape" is correctly set on the video page, but `/trailers`, `/real-films`, and `/generate` all reuse the same homepage title). Each route needs a unique `<title>` tag.

### 6.6 No `sitemap.xml` `<lastmod>` on Video/Profile Entries

The sitemap references all 16 video pages and 8 creator profile pages but provides no `<lastmod>` dates for these entries. For dynamic content pages, `<lastmod>` helps crawlers prioritize re-indexing.

### 6.7 `robots.txt` Also Disallows `/upload` and `/dashboard` — Correct, but `/generate` Should Be Reviewed

`/generate` is disallowed from crawlers, yet the Generate page shows publicly visible content (credit pricing, tool descriptions) that could have SEO value. Consider whether this disallow is intentional.

## 7. Backend / Functional Gaps

### 7.1 No Video File Hosting / CDN Integration

The most fundamental backend gap: no video files are connected to the video player. The platform's entire value proposition — streaming AI short films — is non-functional. There is no observable CDN, no video manifest (HLS/DASH), no `<video src>`, no streaming API call in the network layer.

### 7.2 Platform Stats Are Hardcoded

The figures "16K+ Films Uploaded," "3.2K Emerging Creators," "48+ Countries," and "4 AI Models" appear to be hardcoded in the HTML rather than fetched from a backend API. When the platform has real users these numbers must be replaced with live database-driven counts.

### 7.3 AI Cinema Index Has No Data Source Connected

The `/real-films` page renders an empty table. No API call populates it. The film data from the listed sources (WAIFF, Runway Film Festival, etc.) has not been ingested or seeded.

### 7.4 "Tip" / Tipping Feature Has No Backend

The 💛 "Tip" button appears on every film card across all pages but produces no visible action. There is no tipping flow, payment modal, or error message. This appears to be a stub feature with no backend implementation.

### 7.5 "Save" and "Follow" Buttons — Auth-Gated Behavior Unclear

On the video detail page, the "+ Save" button and "+ Follow" button on the creator card do not visibly respond to clicks when unauthenticated. There is no prompt to sign in, no tooltip, no toast notification. The expected UX (prompt to sign in) is missing.

### 7.6 Revenue Share Claim — No Mechanism Visible

The pricing page and homepage feature list both advertise "Revenue share on featured films" as a Creator plan benefit and "Revenue share on all published films" as a Pro benefit. No mechanism for this is visible anywhere in the platform — no earnings dashboard, no payout configuration, no documentation.

### 7.7 `SearchAction` Schema Points to Disallowed URL

The homepage JSON-LD `SearchAction` target is `https://madtape.com/search?q={search_term_string}`, but `/search` is disallowed in `robots.txt`. Google's Sitelinks Searchbox requires the search endpoint to be crawlable.

## 8. Security / Performance Notes

### 8.1 HTTPS — OK

The site correctly serves over HTTPS with a valid certificate. No mixed-content issues observed.

### 8.2 Cookie Consent — Partially Functional

The cookie consent banner correctly presents three options (Decline All, Necessary Only, Accept All). The choice is stored in `localStorage` as `__madtape_cookie_consent`. However:
- The "Cookie Policy" link in the banner points to `/cookie-policy` which returns 404 — users cannot read the policy before consenting.
- There is no way for a user to change their consent after dismissing the banner, other than clearing localStorage. A re-open mechanism should exist (a floating cookie icon does appear in the bottom right — verify it triggers the banner).

### 8.3 No Security Headers Observed

Because the site is on GitHub Pages, custom HTTP security headers (CSP, X-Frame-Options, Referrer-Policy, Permissions-Policy) cannot be set at the server level. This is a platform limitation, not a code issue, but should be addressed if moving to Vercel/Netlify/Cloudflare where headers can be configured.

### 8.4 Firebase API Key in Client-Side Code

Firebase Auth is initialized client-side. While Firebase API keys in frontend code are by design not secret (they identify the project, not grant admin access), the Firebase project should have App Check and proper security rules configured to prevent abuse (unauthorized data writes, credential stuffing, etc.).

### 8.5 GitHub Pages Infrastructure Exposure

The 404 error pages explicitly reveal "GitHub Pages" as the hosting provider, including links to GitHub's documentation. This exposes the infrastructure stack to anyone who navigates to a broken URL. A custom 404 page would prevent this.

### 8.6 OG Image Has a Space-Encoded Filename

The og:image URL is `https://madtape.com/uploads/panel%201-b5d859a2.png` — the source filename contained a space (encoded as `%20`). While it resolves correctly (confirmed HTTP 200), using spaces in asset filenames is bad practice and can cause cache/CDN issues. Rename to `panel-1-b5d859a2.png`.

### TASK 1 — Fix SPA Routing on GitHub Pages (or migrate host)

**Issue:** All routes except `/` return GitHub Pages 404 on direct access  
**Page/Location:** Entire site, all routes  
**Priority:** Critical  
**Recommended fix:** Option A: Add a `404.html` that replicates the SPA shell and includes the GitHub Pages SPA redirect script (copies the path into the URL hash or session storage and redirects to `/`). Option B (preferred): Migrate hosting to Vercel, Netlify, or Cloudflare Pages, which natively support SPA fallback with a single config line. Add `vercel.json` with `"rewrites": [{ "source": "/(.*)", "destination": "/index.html" }]`.  
**Acceptance criteria:** Every URL in the sitemap, when pasted directly into a browser, loads the correct page content rather than a 404. No GitHub Pages branding appears anywhere.
